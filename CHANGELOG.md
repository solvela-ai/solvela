# Changelog

All notable changes to Solvela (formerly RustyClawRouter), in reverse chronological order.

## 2026-06-17 — OpenAPI-first x402 discovery surfaces: `GET /openapi.json` (+ `x-payment-info`), `GET /.well-known/x402`, favicon

OpenAPI-first x402 discovery crawlers (x402scan and similar) previously marked Solvela "strict non-invocable / skipped" because both `/openapi.json` and `/.well-known/x402` 404'd. Per x402scan's discovery precedence (OpenAPI → `/.well-known/x402` → endpoint-only), a resource is indexed as *payable + invocable* only when the served OpenAPI carries, on the paid operation: non-empty `accepts[]` (already on the live 402), an input request-body schema (already present: `ChatCompletionRequest`), AND an `x-payment-info` extension. This adds those two discovery surfaces plus the `x-payment-info` hint, all **additive** — **no change to the live 402 wire contract, signing, verification, or any USDC math on the paid path**. New public, unauthenticated routes: `GET /openapi.json` serves `docs/openapi.json` **verbatim** via `include_str!` (single source of truth — the same file the `tests/openapi_contract.rs` drift guard embeds and the pay.sh catalog sidecar mirrors, so served bytes and contract-checked bytes cannot diverge); `GET /.well-known/x402` returns `{ "version": 1, "resources": ["{public_url}/v1/chat/completions"] }`, resolving `public_url` through the **same** helper the A2A AgentCard uses (configured `server.public_url`, `http://{host}:{port}` dev fallback — never hardcoded `api.solvela.ai`, so it is correct in any deployment); `GET /favicon.ico` serves a minimal embedded 16x16 ICO to clear the discovery audit's `FAVICON_MISSING` flag. `docs/openapi.json` gains the `x-payment-info` extension on `POST /v1/chat/completions` — `protocols: ["x402"]`, `price: { mode: "dynamic", currency: "USD", min: 0.000001, max: 1.00, description: ... }` — where `mode: "dynamic"` is **authoritative** and `min`/`max` are **non-binding** static discovery hints; `min` is the genuine per-request floor (1 atomic USDC = $0.000001 = the cheapest non-zero model at (1 in, 1 out) with the 5% fee applied once, matching `discovery_floor_atomic`), `max` ($1.00) brackets a representative ~128k-context request on the most expensive model (Claude Opus 4.6, $5/$25 per M → ~$0.887 worst-case). The `servers` list now leads with the canonical `https://api.solvela.ai` (with `https://solvela-gateway.fly.dev` kept as the direct Fly host). Tests-first via `solvela-x402` + `solvela-fintech`: 4 new contract tests (`/openapi.json` byte-verbatim + `x-payment-info` shape; `min <= max` spec self-check; `/.well-known/x402` shape; favicon image) plus a `cost.rs` unit test pinning the advertised `min` ≤ the real `config/models.toml` registry floor (fail-closed — we can never advertise a floor above the cheapest payable cost). `gateway` lib cost-module tests + 15 `openapi_contract` integration tests green; fmt + clippy clean; the component-schema drift guard is unaffected (the extension sits on the operation, outside `components.schemas`). **Follow-up (not done here):** the pay-skills catalog sidecar (separate repo) needs a `docs/openapi.json` re-sync since the spec changed (servers + `x-payment-info`). Not yet deployed — additive discovery surfaces, rides the next Fly release.

## 2026-06-16 — Unsigned escrow-deposit-tx API for external signers (BYO-wallet funding, PR 1)

[#597](https://github.com/solvela-ai/solvela/pull/597) — new `POST /v1/escrow/deposit-tx` returns an **unsigned** escrow-deposit Solana message (base64) plus a `decoded_intent` object, so any external signer (browser wallet, KMS, hardware) can verify-then-sign and submit it — the gateway holds **no private key** on this path. First PR of the BYO-wallet "Medium" funding slice (lets users fund an agent's escrow with a wallet they already control, without putting the main key in the agent runtime): it is the interop primitive that makes an escrow fundable by any x402-capable signer without the Solvela SDK, and unblocks the dashboard connect-wallet flow + `.sol` display in later slice PRs. **Wire-clean by construction:** the pure `solvela-escrow-tx` crate gains a pubkey-only `build_deposit_message` (+ `derive_deposit_addresses`) that the existing keypair-based `build_deposit_tx` now calls as its sole message-construction path, so the signed and unsigned paths cannot drift and `GOLDEN_VECTOR_B64` is **byte-identical** (no SDK/wire change; no new deps — stays solana-sdk-free). The handler validates every input (base58 pubkey, 32-byte `service_id`, canonical atomic-USDC `amount`, clamped expiry window), rate-limits per real TCP peer IP before any work, reads a cached slot + a `confirmed`-commitment recent blockhash, and fails closed on RPC with sanitized errors (no RPC internals or live slot leaked); `provider`/`usdc_mint`/`escrow_program_id` are sourced from gateway config so a caller cannot redirect funds. Startup now also validates `recipient_wallet` (fatal only when escrow is configured). Two-round money-path review (rust + silent-failure + security + type-design, then an independent pass that caught a real fixture-revalidation test regression round 1 missed). `solvela-escrow-tx` 23 (golden-vector parity byte-identical) + `solvela-x402` 148 + gateway 825 lib + 269 integration green; fmt + clippy clean. **Not yet deployed** — additive endpoint, rides the next Fly release.

## 2026-06-15 — x402 discovery 402 for unpaid probes (registry health-checks); deployed Fly v409

[#584](https://github.com/solvela-ai/solvela/pull/584) — `/v1/chat/completions` now advertises its x402 `402` payment challenge to UNPAID probes so x402 registry health-checkers can discover it. Probers GET the URL or POST an empty/minimal body; previously those hit 405/400/422 (the 402 only fired after a full `ChatRequest` deserialized), so registries reported "degraded / unknown protocol". The endpoint now returns an x402 **discovery 402** before body validation: `GET → 402`, unpaid empty/invalid `POST → 402`. It reuses the shared challenge builder (byte-shape identical to the real 402 — legacy snake_case body + canonical base64 `PAYMENT-REQUIRED` header), advertising the same `accepts` (scheme(s), Solana CAIP-2, the configured USDC mint, `payTo`) with a non-binding floor amount = the cheapest priced model's per-request cost (atomic USDC, fail-closed conversion, 5% fee applied once; `warn!` if no model is priced). A valid POST still returns the exact per-request quote; a request carrying `PAYMENT-SIGNATURE` is byte-unchanged (bad body still 4xx, so paying clients keep validation errors). The discovery path is read-only and structurally cannot reach verify/settle/provider/spend (test-pinned). Implemented by the money-path engineer (tests-first, `solvela-x402` + `solvela-fintech`); round-1 review (rust-reviewer + silent-failure-hunter) — the shared HIGH on the discovery `amount` format was a verified false positive (the real wire `amount` is an atomic integer `"68815"`, which the discovery `"1"` mirrors — confirmed against live prod; the proposed change would have introduced a 1,000,000× error), and the one actionable finding (no signal on the degenerate all-unpriced registry) was fixed with a `warn!`. 9 discovery integration tests + 2 floor unit tests; `gateway` lib 811 + integration green; fmt + clippy clean. **Deployed Fly v409** and live-verified: GET, empty POST, and `{}` all return 402 with a decodable canonical challenge; a valid POST still returns the exact quote. Closes the registry-discoverability gap surfaced by live x402 health-check probes.

## 2026-06-13 — A2A exactly-once settlement lock + settle-then-fail reorder; deployed Fly v406 (also takes #567/#568 live)

[#574](https://github.com/solvela-ai/solvela/pull/574) (`1e741bbf`, closes [#566](https://github.com/solvela-ai/solvela/issues/566)) — closes a pre-existing A2A concurrency gap: two concurrent `message/send` calls for one `taskId` with two *different* valid transactions each passed their own per-tx replay check and `validate_submitted_against_offer` (which binds to the quoted amount, not a specific tx), so both reached `verify_and_settle` → two `spend_logs` rows + two receipts for one logical task. An atomic Redis `SET NX EX` per-task settlement lock (`solvela:a2a:settle_lock:{task_id}`, TTL 120s) is now acquired **before** `verify_and_settle`: the CAS winner settles, the loser is cleanly rejected (`solvela_a2a_concurrent_settlement_rejected_total{reason="concurrent"}`) without settling; the lock is held on success (self-expires via TTL so an in-flight loser can't re-settle moved funds) and released on pre-settlement failures so a corrected retry isn't stranded; there is deliberately no in-memory fallback (it couldn't serialize across gateway instances — the multi-instance race the lock exists to close). Paired with a **CRITICAL reorder**: model resolution + the prompt guard now run before lock acquisition and settlement (mirroring the chat path), so a deterministic pre-check failure (bad model id, guard-blocked content) can no longer leave a task settled-but-unledgered — a window the lock alone would have *worsened* by holding it 120s. A post-settle provider failure (funds already moved) ledgers the **quoted total** and holds the lock; the raw provider error is no longer echoed to the client (`ERR_PROVIDER_ERROR`, GHSA-cgqx-mg48-949v consistency). Fail-closed no-Redis / lock-store arms (`solvela_a2a_settle_lock_unavailable_total{reason}`), plus `solvela_a2a_settle_lock_release_failed_total` and `solvela_a2a_task_state_update_failed_after_settle_total`. Two-round money-path review (round 1: rust-reviewer + silent-failure-hunter + pr-test-analyzer + independent security; round 2: a fresh independent pass on the cumulative diff → APPROVE) — round 2 caught a **HIGH** (the post-settle provider-error leak) and a money-path test gap (amount asserted `> 0` instead of the exact quoted total) that round 1 missed. Red-first tests pin: deterministic pre-checks reject before any lock/settlement; a post-settle provider failure writes exactly one ledger row at the exact quoted total and holds the lock; the headline race settles exactly once — and the pre-existing [#561](https://github.com/solvela-ai/solvela/issues/561)/[#567](https://github.com/solvela-ai/solvela/pull/567) ledger assertions were hardened from tracing-capture to durable Postgres row counts. `gateway` lib 783 + integration 238 + `solvela-x402` 144 green; fmt + clippy clean. **Deployed Fly v406** and live-verified (`/health` ok, A2A agent card serving, migrations applied). As the first release since v405, v406 also takes the previously-undeployed [#567](https://github.com/solvela-ai/solvela/pull/567) (A2A receipts) and [#568](https://github.com/solvela-ai/solvela/pull/568) (E1 org rollups) live. **Follow-up filed:** [#573](https://github.com/solvela-ai/solvela/issues/573) — a fencing token for the unfenced `release_settle_lock` `DEL`, and the narrow re-settle window if `update_task_state(Failed)` also fails after a post-settle provider failure (lock TTL 120s < task TTL 600s — a design tradeoff vs. the crashed-before-settle retry case).

## 2026-06-13 — Org budget rollups + analytics polish (E1): read-only org spend-control reporting

[#568](https://github.com/solvela-ai/solvela/pull/568) — E1 of the Agent Spend Control Plane. Read-only reporting over `spend_logs` — no hot-path change, no budget-enforcement change, no migration. The already-public `GET /v1/orgs/:id/stats` gains: an **org budget-vs-spend rollup** computed as the SUM of the org's teams' `team_budgets` limits per period (no `org_budgets` table), honest about partial coverage — an absent team budget counts as unlimited (reported `null`, not `0.0`), with `teams_total` + `teams_with_{hourly,daily,monthly}_budget` counts so a partial sum can't be misread as a real ceiling. A **double-counting fix**: a wallet in multiple teams of one org was multiplied by the `spend_logs → team_wallets` join fan-out; all row-once aggregations now dedupe via `wallet_address IN (SELECT DISTINCT …)`, counting each spend row once, while `by_team` deliberately still attributes a shared wallet under each team (pinned by test). New `by_day` time series; clamped `limit`/`offset` pagination replacing a hardcoded `LIMIT 10`, with a stable tie-break; and `by_tenant` + `by_vendor` breakdowns — the latter summing the [#555](https://github.com/solvela-ai/solvela/pull/555)/[#560](https://github.com/solvela-ai/solvela/pull/560) vendor settled/fee-receivable atomic columns per vendor wallet, formatted via the canonical `atomic_to_usdc_string` (no f64 on money, fail-closed `u64::try_from`). All new fields additive; `get_org_stats`/`get_team_stats` shape unchanged. Single review round (rust-reviewer), a deliberate step-down from the P1/P2 two-round money-path process because read-only reporting cannot gate, charge, or deny a request; 6 new DB-backed tests through the real route, `orgs_routes` 26/26 green. Stays in the public gateway repo (extends already-public endpoints; the open-core line is at E2 invoicing / E3 cost-center). A 3-agent research pass decided **against** org-level budget enforcement: the org tier is a reporting/alerting boundary across the comparable products (Ramp/Brex/AWS/GCP, agent-wallet tooling), hard caps belong at the leaf wallet/team (already enforced), and `team_wallets` permits a wallet across orgs so an org hard-cap is schema-ambiguous. Not yet deployed — rides the next Fly release.

## 2026-06-12 — Client-facing payment receipts (P2): durable `receipts` ledger, `X-Solvela-Receipt` header, public `GET /v1/receipts/{id}`; deployed Fly v405

[#560](https://github.com/solvela-ai/solvela/pull/560) — P2 of the settlement-platform track: every paid request now produces client-facing audit evidence. A new `receipts` table (migration 013 — UUID PK, atomic-integer amounts with `>= 0` CHECKs, a `payment_scheme` length cap, and a vendor co-nullability CHECK making half-written vendor rows unrepresentable at the DB layer) is written fire-and-forget **in lock-step with the spend ledger** across all paths: the three chat settling arms including the streaming `EstimateFallback` ([#541](https://github.com/solvela-ai/solvela/pull/541)'s write point, mutation-tested), and the proxy path — vendor receipts at settlement time carrying the [#555](https://github.com/solvela-ai/solvela/pull/555) fee-receivable fields (receipts are the invoice evidence trail for the vendor-absorbs model), plain services at the legacy post-upstream point. No spend row → no receipt, by design; every skip path is observable via `solvela_receipt_skipped_total` reasons. The `X-Solvela-Receipt` response header carries `/v1/receipts/{uuid}` and is emitted only when the receipt is actually retrievable — absent on free-tier ($0), DB-less gateways, and uncollected-payment (`SkipSettleFailed`) responses; for SSE the id is allocated and the header set before the body streams. The public `GET /v1/receipts/{receipt_id}` is capability-by-unguessable-UUIDv4: unknown and malformed ids return byte-identical 404s (no existence oracle), DB-less → 503, rate-capped at **20/min per IP** (5/min for the unknown bucket) via the existing free-tier limiter pattern, checked before any DB work, canonical 429 envelope. Amounts are canonical atomic integers mirroring the spend ledger exactly, with USDC strings derived by pure integer formatting; the escrow semantic-cache discount is reflected (billed < quoted, pinned by test), and the documented divergence from the raw on-chain transfer on agent overpayment is doc-commented and in the OpenAPI description. Wire types are gateway-local — deliberately not `solvela-protocol`, so no SDK version bump; revisit before any SDK ships receipt support. `docs/openapi.json` gained the endpoint (200/404/429/503, response header, three schemas) and the [#539](https://github.com/solvela-ai/solvela/pull/539) contract guard is green with new conformance tests including the live 404. Server logs are de-correlated: `receipt_id` never appears alongside `payer_wallet` on the happy path, so capability URLs can't be harvested from log access. Two-round money-path review: round 1 (rust-reviewer + silent-failure-hunter) fixed two Criticals (silent header-drop, unobservable corrupt-read) plus the co-nullability CHECK; the independent round 2 (security + test-coverage + type-design) fixed one High — the public GET was an unauthenticated per-request DB query behind only the generic 60/min limiter — plus the log de-correlation and mutation coverage for the zero-coverage escrow semantic-cache arm. One finding rejected deliberately: removing `fee_receivable` from the public receipt — it equals `floor(settled×5%)` with the fee percentage publicly documented (discloses nothing non-derivable), and attesting the receivable is the receipt's purpose as invoice evidence. ~25 new tests; 1,136 gateway tests green. Deployed as **Fly v405** the same day and live-verified: the receipts endpoint serves the canonical 404 contract (which also proves migration 013 applied), with health and the 402 path intact — v404, deployed ~3h earlier the same day, had already taken [#555](https://github.com/solvela-ai/solvela/pull/555)/P1 live. **Follow-up filed:** [#561](https://github.com/solvela-ai/solvela/issues/561) — paid A2A requests write neither `spend_logs` rows nor receipts (pre-existing; the completed Task carries only in-band `tx_signature` metadata). Other follow-ups from the PR: the [#556](https://github.com/solvela-ai/solvela/issues/556)-class plain-proxy test seam, the pay-skills catalog sidecar OpenAPI re-sync, and deferred type-design newtypes.

## 2026-06-12 — Per-service `vendor_wallet`: direct-to-vendor settlement with vendor-absorbed fee (P1); Python SDK `solvela-sdk` 0.3.0 published to PyPI

[#555](https://github.com/solvela-ai/solvela/pull/555) — P1 of the settlement-platform track. A marketplace service registered with `vendor_wallet` now settles USDC **directly to the vendor's wallet** — non-custodial, a single transfer, zero wire-format change. The wallet is validated as a Solana pubkey at TOML load and at the admin `POST /v1/services/register` (fail closed), rejected on internal services and when equal to the gateway's own recipient wallet (which would have silently undercharged the agent 5%). **Vendor-absorbs-fee semantics:** the 402 for a vendor service advertises the vendor wallet as `payTo` and the bare listed price (agent-side fee 0; `cost_breakdown` stays truthful); Solvela's 5% (`floor(price×5/100)`, atomic) is recorded at settlement time as a **fee receivable** in `spend_logs` (migration 012: `vendor_wallet`, `vendor_settled_atomic`, `vendor_fee_receivable_atomic` + a partial index) for off-chain invoicing. Services without `vendor_wallet` are byte-for-byte unchanged (`price×1.05` to the global recipient) and regression-pinned; the LLM chat path is untouched. An on-chain two-transfer split was researched and rejected: canonical x402 clients hardcode a single-`TransferChecked` transaction, reference facilitators reject a second SPL transfer, upstream rejected facilitator fund-splitting on trust-minimization grounds ([x402-foundation/x402#1153](https://github.com/x402-foundation/x402/pull/1153)), and it would break golden-vector parity across all four SDKs plus pay-CLI compatibility — the only non-custodial precedent (Coinbase's facilitator) bills off-chain; escrow claim-split takes the fee on-chain later (P4). Verification: a new fail-closed `PaymentVerifier::verify_payment_to` threads the per-service expected recipient into the same hard ATA-derived equality check; the trait default returns `RecipientOverrideUnsupported`, so the escrow verifier inherits it and escrow payments to vendor services are rejected (402) — recipient mismatches are rejected both ways. A vendor receivable whose DB INSERT fails emits an error-level event with full reconciliation fields plus a `solvela_vendor_receivable_write_failures_total` counter. Two-round money-path review (round 1 fixed one Critical — silent receivable-write loss; the independent round 2 found no Critical/High, with all worth-changing-now items landed pre-merge); ~35 new tests, gateway 1,110 + x402 144 green. Not yet deployed — rides the next Fly release; migration 012 applies on startup. **Follow-up filed:** [#556](https://github.com/solvela-ai/solvela/issues/556) — a pre-existing #541-class gap on `main` before this PR: a settled non-vendor proxy payment drops its `spend_logs` row if the SSRF re-check or body-read fails before the deferred post-upstream write; the fix is logging at settlement (a row-timing semantics change) plus an injectable-upstream test seam. The new vendor path already logs at settlement and is unaffected.

[#554](https://github.com/solvela-ai/solvela/pull/554) added the first PyPI publish pipeline for the Python payment SDK — tag-triggered on `sdks/python/v*`, using **PyPI Trusted Publishing (OIDC)**, no long-lived token. Tag `sdks/python/v0.3.0` was pushed and the workflow succeeded 2026-06-12 13:06 UTC; verified live on PyPI: **`solvela-sdk` 0.3.0, license Apache-2.0**. Relative to the published MIT-era 0.2.0 (2026-05-11), 0.3.0 ships native x402 escrow-deposit signing, the [#475](https://github.com/solvela-ai/solvela/pull/475) `TransferChecked` exact-payment fix, and the [#494](https://github.com/solvela-ai/solvela/pull/494) escrow-program-id pinning (incl. `EscrowProgramMismatchError`); the version jump resolves the collision with the already-published 0.2.0, whose in-repo content had drifted without a bump. This closes the "Python `solvela-sdk` PyPI release is deferred" note from the 2026-06-06 entry and is the first PyPI release since the 2026-05-31 Apache-2.0 relicense — the PyPI license metadata is now flipped.

## 2026-06-04 — Cross-SDK `exact`-payment fixes (Python + TypeScript), Go escrow signing, Rust proxy 402 fix

Four SDK-only PRs landed, all on the x402 payment path. The unifying thread: the live gateway verifier has required SPL **`TransferChecked` (ix 12)** for `exact` USDC payments since `e4f0db45` (so the mint is on-chain-verifiable and a plain `Transfer` can't spoof it), and two SDK signers had drifted to plain **`Transfer` (ix 3)**, silently failing verification in production. No gateway redeploy — the verifier was already correct.

- **Python SDK — `exact` uses `TransferChecked`** ([#475](https://github.com/solvela-ai/solvela/pull/475)). Switched `createTransfer`→`transfer_checked` (mint + 6 decimals), pinned a byte-exact `EXACT_GOLDEN_VECTOR_B64`, and added a drift guard that reads the canonical value from the Rust source so the Python and Rust signers can't silently diverge. The Rust reference signer already emitted `TransferChecked`; this PR also re-pins the gateway acceptance test.
- **TypeScript SDK — `exact` uses `TransferChecked`** ([#479](https://github.com/solvela-ai/solvela/pull/479), closes [#477](https://github.com/solvela-ai/solvela/issues/477)). `@solvela/sdk` consumers' `exact` payments were being rejected live. Fixed by `createTransferCheckedInstruction` (mint + `USDC_DECIMALS=6`) plus byte-exact wire assembly: web3.js's `Transaction.serialize()` orders accounts by instruction-appearance within a writability partition, whereas the Solana Rust SDK byte-sorts within the partition (flipping token-program vs mint for `TransferChecked`), so the code compiles a legacy `Message` with explicit Rust-SDK ordering, signs the raw bytes via a new in-boundary `Wallet.signMessage` (Node `crypto` ed25519, no new dependency), and assembles `compact-u16(1) || sig || msg`. Golden-vector parity + drift guard mirror the Python tests.
  - A 6-agent `/review-pr` pass caught a **Critical** introduced by the change: the public, barrel-exported `buildExactTransferTx` validated the amount only on the indirect path, so a direct call with a negative amount wrapped via `BigInt(-1)` to `0xFFFFFFFFFFFFFFFF` (~18.4 quintillion atomic USDC), and zero/float truncation slipped through. Fixed (`f1c15167`) by moving `assertValidAmount` into the builder, with tests for direct-call rejection (no RPC), non-`Error` RPC wrapping, and invalid recipients.
- **Go SDK — native x402 escrow-deposit signing** ([#474](https://github.com/solvela-ai/solvela/pull/474)). Produces the canonical escrow-deposit wire format (PDA seeds `[b"escrow", agent, service_id]`, Anchor `deposit` discriminator, `EscrowPayload` header) byte-for-byte against the golden vector. Adds a `SchemeCapable` interface so `findCompatibleScheme` filters to schemes the signer can actually fulfill — the gateway lists `exact` first, but the Go signer only signs `escrow`, so without this the Go client was dead-on-arrival; `exact` remains an explicit `UnimplementedSigner` error rather than a silent mis-route.
- **Rust client-proxy — strip `accept-encoding` so 402 bodies stay parseable** ([#476](https://github.com/solvela-ai/solvela/pull/476)). The proxy forwarded the caller's `accept-encoding: gzip` to the gateway; a fronting edge then compressed the 402 body and the proxy's `serde_json::from_str` of the `PaymentRequired` payload failed (surfaced via CowAgent's Python openai client, which always advertises gzip). reqwest is built with no decompression features and the gateway applies no compression layer, so stripping the outbound header is the correct fix.

**Follow-up filed** ([#480](https://github.com/solvela-ai/solvela/issues/480)): implement TS SDK escrow deposit signing and gate scheme selection on signer capability (mirroring Go's `SchemeCapable`). Until then, an `escrow` scheme passed to the TS signer fails closed with a clear `SignerError` — a strict improvement over the prior behavior of silently producing an `exact` transfer.

## 2026-05-22 — Semantic cache (Tier 2), Phase 1

Added an optional embedding-similarity cache tier in front of the existing exact-match cache. A paraphrase of a previously-answered prompt can now hit the cache instead of calling the upstream LLM. **Off by default** (`[cache.semantic].enabled = false`) — enabling it is the only behaviour change.

- **Cache module split** — `cache.rs` → `cache/{mod,exact,semantic,embedder}.rs`. The exact tier and shared infra (replay protection, raw KV) are unchanged.
- **Embedder** — local `bge-small-en-v1.5` (384-dim) via `fastembed`/`ort`, behind an `Embedder` trait so an API-backed model can be swapped in. ~13 ms p50 on CPU; Mutex-guarded (≈75 emb/s per process — a model pool is future work).
- **Semantic store** — RediSearch HNSW cosine index, model-scoped (a cached `openai/...` answer is never served to `anthropic/...`), threshold-gated (default cosine ≥ 0.85). Stays wallet-agnostic (rule #16). Writes are fully fire-and-forget (rule #9): embedding *and* the Redis write run off the hot path.
- **Discount** — a semantic hit bills `hit_price_percent` of the full price (default 30 → 70% off), realised on the **escrow** scheme by claiming only the discounted amount (the remainder refunds to the agent). The direct-transfer (`exact`) scheme settles the full amount up front, so the discount does not apply there — by design (the cryptographic-commitment + on-chain bond that would make discounts trustless on every scheme are Phases 2–3).
- **Config** — new `[cache.semantic]` section (`enabled`, `threshold`, `hit_price_percent`, `ttl_secs`, `model_cache_dir`). Requires Redis-with-RediSearch (compose now uses `redis/redis-stack-server:7.4.0-v3`); degrades gracefully to the exact cache if Redis/RediSearch or the model is unavailable (rule #12).
- **Privacy** — embeddings are partially invertible; see `SECURITY.md` for the prompt-embedding note. The model is fetched from the Hugging Face hub on first run.

Built test-first (RED→GREEN per unit) and reviewed by the `rust-reviewer` agent before wiring. New tests: embedder (10), semantic store (13, against live redis-stack), cost/discount math (integer-only), config parsing, and HTTP-level integration (paraphrase served from cache / unrelated misses). Model- and Redis-dependent tests skip gracefully where those deps are absent.

A subsequent multi-agent review pass (code / tests / silent-failure / type-design / comments) caught and fixed several issues before merge: the semantic tier wasn't populated in production (now written on upstream responses); a usage-less hit could bill zero (now estimate-fallback or fall-through, never free); per-wallet **budget counters and the spend log recorded the full price on a hit instead of the discounted price** (now discounted — they were over-consuming budget and would deny agents prematurely); invalid `[cache.semantic]` config (zero/over-range `hit_price_percent` or `threshold`) is now a **fatal startup error** rather than a silently-disabled cache; sampling params (`temperature`/`top_p`) are now part of the semantic key so they can't cross-hit; write backpressure (a `Semaphore`) bounds the embed-per-miss fan-out; and a non-finite / unparseable similarity score is rejected/logged rather than silently serving or missing. Exact-scheme payments receive no discount by design (the full amount settles before the cache is consulted).

A final cloud **ultrareview** round then closed seven more findings, several of which the earlier passes had reported as fixed but hadn't truly addressed:

- **Sampling-param gating actually works now.** The earlier "params in the key" fix appended a `temperature=…` line to the *embedded text*, but two prompts differing only in temperature embed to near-identical vectors (cosine ≈ 0.99 ≫ 0.85), so the line was invisible to the KNN gate and the wrong sampling regime was still served. Its test only asserted string inequality, not lookup separation. Sampling params are now **exact RediSearch TAG predicates** (`@temperature` / `@top_p`, index versioned to `_v2`); the regression test drives the real lookup (store at `temperature=0`, query at `temperature=2` → **miss**).
- **Exact-scheme spend now records the full price.** The discount is only realised on escrow (claim less + refund); on `exact` the agent settles in full on-chain with no refund, so logging the discounted price under-counted real spend. The scheme gate is now an extracted, unit-tested pure function.
- **Usage-less hits reconcile the budget reservation.** A semantic hit whose cached response carried no `usage` skipped `log_spend` entirely, leaving the `check_budget` reservation un-settled and over-consuming the wallet's budget (~70% over). It now logs to reconcile.
- **Cached usage is capped before pricing.** A hit was priced from the stored (uncapped) token counts, bypassing the provider-trust cap and over-billing; it's now capped against the current request first.
- **Oversized prompts fall through.** BGE silently truncates at 512 tokens, so two long prompts sharing a >512-token prefix could collide and serve the wrong answer; prompts past a ~2000-char budget are no longer cached or served.
- **Config + dev nits.** `ttl_secs = 0` (which makes `EXPIRE` delete entries on write → silent all-miss cache) is now a fatal startup error; the dev `docker-compose` Redis no longer passes a literal `--save ''` (Compose doesn't strip the quotes). The redis-backed tests are now serialized so the shared index can't be wiped mid-run under parallel `cargo test`.

### [#320](https://github.com/solvela-ai/solvela/pull/320) — x402 protocol downgrade warning in signer-core (#173 L1 SDK)

Picked from [#173](https://github.com/solvela-ai/solvela/issues/173)'s LOW bucket. Before this change, `parse402()` silently accepted any non-negative `x402_version` (the schema enforced only `minValue(0)`), so a gateway returning `x402_version: 0` or `1` against a client signing `2` parsed cleanly with no signal that the protocol contract had drifted.

`parse-402.ts` now emits a `console.warn` on `gateway_version < X402_VERSION_CLIENT`, deduplicated to **one warn per unique downgraded version per process** so a tight request loop doesn't log-flood while still surfacing the regression on first occurrence. `X402_VERSION_CLIENT = 2` is now exported from `schema.ts` as a single source of truth; `sign.ts` aliases it locally to preserve call-site readability.

CodeRabbit on the PR flagged a theoretical Set-balloon vector — a malformed gateway sending `0.0001, 0.0002, ...` could grow the dedup Set unboundedly. CodeRabbit suggested normalizing the dedup key with `Math.trunc()`; the structural fix instead was to add `integer()` to the `x402_version` schema pipe so fractional values are rejected at parse time (throw, not warn) — the warn path then never sees them. 4 new tests cover the downgrade-warn behavior; 1 additional test covers the fractional-version rejection. 88/88 → 89/89 → 90/90 across the iteration.

Downstream regression check: 86/86 mcp, 70/70 openclaw-provider, 353/353 ai-sdk-provider all pass after the signer-core change.

### Protocol wire fix ([#229](https://github.com/solvela-ai/solvela/pull/229))

`ModelInfo` is the on-the-wire record at `GET /v1/models` and the sibling SDKs (Python, Go, TypeScript) deserialize it directly. Pre-0.3.0, `solvela-protocol` derived `Serialize` / `Deserialize` on flat top-level fields (`input_cost_per_million`, `supports_streaming`, …), but the **gateway emits a NESTED shape** — `pricing.input_per_million` and `capabilities.streaming`. Net effect: every SDK consumer silently parsed every response with all-zero pricing and all-false capabilities. No panic, no error, no log line. Pure zero-fill.

The fix replaces the derives with hand-rolled `Serialize` / `Deserialize` impls translating between the flat Rust struct (gateway-internal API preserved unchanged) and a private `ModelInfoWire` carrying the nested shape, with private `Pricing` / `Capabilities` sub-structs. `Deserialize` is intentionally lossy: `model_id`, `supports_structured_output`, `supports_batch`, `max_output_tokens` are not on the wire and default to empty / `false` / `None`. Contract documented at the impl as SDK-consumer-only; gateway-internal code constructs from the registry and never round-trips through JSON.

Specialized 5-agent review (rust-reviewer, security-reviewer, type-design-analyzer, silent-failure-hunter, pr-test-analyzer) caught a CI-blocker (`derivable_impls` clippy lint on `Capabilities::default` — switched to `#[derive(Default)]`), a redundant `.map_err(de::Error::custom)?` (simplified to `?`), and a missing test for the partial-pricing-block case (block present but field absent → silent 0.0; new test pins the contract). Deferred follow-ups tracked in `STATUS.md` Known follow-ups.

5 unit tests in `mod tests` covering serialize-emits-nested-shape, deserialize-of-actual-gateway-payload (the regression case), defensive-defaults for missing blocks, partial-block silent-zero-fill, and round-trip preservation.

## 2026-05-08 — Escrow program hardening

Pre-launch security review of `programs/escrow/` surfaced two latent settlement-path footguns. Both fixed in source ([PR #160](https://github.com/solvela-ai/solvela/pull/160)) and the bytecode redeployed to mainnet at `9neDHouXgEgHZDde5SpmqqEZ9Uv35hFcjtFEPxomtHLU` on slot 418438627 (tx `2Rp69yKfyxeeawrFRPZbLma9NytxEXSz8PeWPdNYzWm4e3Fr2xihP3T23PiwDB9xYbnUwN8kmsnrgBKjP2dbBbuE`). `getProgramAccounts` returned zero accounts at the time of redeployment — both flaws were latent and unexploited.

### Findings (proactively patched)

- **Claim-vs-refund race at the expiry boundary** — once `slot >= expiry_slot`, both `claim` and `refund` were simultaneously valid. An adversarial provider could race the agent at the deadline and capture the deposit. New guard requires `Clock::slot < expiry_slot` for `claim`.
- **Refund deadlock when the agent's USDC ATA had been closed** — agents who closed their ATA after deposit (a normal post-deposit move that reclaims rent) would find both `refund` and `claim`'s refund leg failing. The funds would have been permanently stuck in the vault PDA. Both instructions now use `init_if_needed` so the agent's ATA is recreated on the fly when needed.

### Secondary hardening (same PR)

- `USDC_MINT` feature-gated (`mainnet` selects `EPjFW…`, default selects devnet). Same source compiles for any cluster without code edits.
- `deposit` rejects `provider == agent` and `provider == Pubkey::default()` (catches misconfigured client calls before funds are locked).
- `expiry_slot` capped at `now + MAX_ESCROW_SLOTS` (~1 day at 400ms/slot).
- `claim`'s `agent` constraint switched from `SystemAccount` → `UncheckedAccount` (unblocks PDA-/program-owned agents in the future).
- `ClaimEvent` gains a `deposited` field for indexer disambiguation.
- `refund` rejects `vault_amount == 0`; `claim` uses `checked_sub` for the refund computation.
- 7 new tests added (5 integration covering claim-after-expiry, ATA-closed recovery, self-provider rejection, excessive-expiry rejection; 2 unit covering the new event field and the slot ceiling).

- `cargo build-sbf -- --features mainnet` produced bytecode hash `2293edfce3a0e7b1b0332bc32d9f7a9e58105a2a3f825ee05d8a4f7fbf57bf26`, matching the on-chain dump truncated to source size.
