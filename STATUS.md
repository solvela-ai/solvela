_2026-06-12 (later) — **P2 of the settlement-platform track shipped and deployed: client-facing payment receipts — every paid request now produces retrievable audit evidence.** [#560](https://github.com/solvela-ai/solvela/pull/560) (`28fc8763`) adds a `receipts` table (migration 013: UUID PK, atomic-integer amounts with `>= 0` CHECKs, a `payment_scheme` length cap, and a vendor co-nullability CHECK making half-written vendor rows unrepresentable at the DB layer), with receipt rows written fire-and-forget **in lock-step with the spend ledger** across all paths — the three chat settling arms including the streaming `EstimateFallback` ([#541](https://github.com/solvela-ai/solvela/pull/541)'s write point, mutation-tested), plus the proxy path (vendor receipts at settlement time carrying the [#555](https://github.com/solvela-ai/solvela/pull/555) fee-receivable fields — receipts are the invoice evidence trail for the vendor-absorbs model; plain services at the legacy post-upstream point). An `X-Solvela-Receipt` response header carries `/v1/receipts/{uuid}`, emitted only when the receipt is actually retrievable — absent on free-tier ($0), DB-less gateways, and uncollected-payment (`SkipSettleFailed`) responses; for SSE the id is allocated and the header set before the body streams. _2026-06-12 — **P1 of the settlement-platform track merged: per-service `vendor_wallet` — a marketplace service can settle USDC directly to its vendor's wallet, with Solvela's 5% recorded as an off-chain fee receivable.** [#555](https://github.com/solvela-ai/solvela/pull/555) (`5c0ff0c5`) lets a service registered with `vendor_wallet` settle **directly to the vendor's wallet** — non-custodial, a single transfer, zero wire-format change. The wallet is validated as a Solana pubkey at TOML load and at the admin `POST /v1/services/register` (fail closed), and rejected on internal services and when equal to the gateway's own recipient wallet (which would have silently undercharged the agent 5%). Semantics are **vendor-absorbs-fee**: the 402 for a vendor service advertises the vendor wallet as `payTo` and the *bare listed price* (agent-side fee 0; `cost_breakdown` stays truthful), while Solvela's 5% (`floor(price×5/100)`, atomic) is recorded at settlement time as a **fee receivable** in `spend_logs` (migration 012: `vendor_wallet`, `vendor_settled_atomic`, `vendor_fee_receivable_atomic` + a partial index) for off-chain invoicing. Services without `vendor_wallet` are byte-for-byte unchanged (`price×1.05` to the global recipient) and regression-pinned; the LLM chat path is untouched. **Why invoicing and not an on-chain split:** a two-transfer-instruction payment was researched and rejected — canonical x402 clients hardcode a single-`TransferChecked` transaction, reference facilitators reject a second SPL transfer, upstream rejected facilitator fund-splitting on trust-minimization grounds ([x402-foundation/x402#1153](https://github.com/x402-foundation/x402/pull/1153)), and it would break golden-vector parity across all four SDKs plus pay-CLI compatibility; the only non-custodial precedent (Coinbase's facilitator) bills off-chain, and escrow claim-split takes the fee on-chain later (P4). Verification threads the per-service expected recipient into the same hard ATA-derived equality check via a new fail-closed `PaymentVerifier::verify_payment_to`; the trait default returns `RecipientOverrideUnsupported`, so the escrow verifier inherits it and escrow payments to vendor services are rejected (402) — recipient mismatches are rejected both ways (vendor service paid to the global wallet and vice versa). A vendor receivable whose DB INSERT fails emits an error-level event with full reconciliation fields plus a `solvela_vendor_receivable_write_failures_total` counter — never an untagged warn. Two-round money-path review: round 1 (rust-reviewer + silent-failure-hunter) caught and fixed one Critical (silent receivable-write loss); the independent round 2 (security + test-coverage + type-design) found no Critical/High, and its worth-changing-now items (`PaymentTarget` enum, `u64` settlement amounts, self-recipient registration guard, must-add tests incl. escrow-fail-closed, an i64-overflow pre-quote guard, the fee-floor zero-receivable case) all landed pre-merge. ~35 new tests; gateway 1,110 + x402 144 green. **Follow-up filed:** [#556](https://github.com/solvela-ai/solvela/issues/556) — a pre-existing #541-class spend-row gap on the non-vendor proxy path (see Known follow-ups; on `main` before this PR — the new vendor path logs at settlement and is unaffected). **Not yet deployed** — rides the next Fly release; migration 012 applies on startup._
